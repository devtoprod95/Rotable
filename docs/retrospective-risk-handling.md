# ROTABLE 프로젝트 회고록 — 장애·문제 상황 대비 기록

> 서비스 1차 개발을 마친 시점에서, **운영 중 발생할 수 있는 에러·문제 상황을 어떻게 대비했고, 앞으로 무엇을 해야 하는지** 정리한 회고 문서입니다.
> 내용은 실제 코드 기준이며, "대비된 것"과 "아직 비어 있는 것"을 구분해 적었습니다.

| 항목 | 내용 |
|---|---|
| 대상 서비스 | ROTABLE — 로테이션 소개팅 운영 플랫폼 (Laravel 13 / React + Inertia / Reverb) |
| 작성 목적 | 운영 리스크 점검, 설계 의사결정 기록, 후속 개선 과제 도출 |
| 작성 시점 | 2026-11-13 |
| 범위 | 동시성 · 멱등성(중복 요청) · 데이터 정합성 · 외부 의존/실시간 장애 · 운영 실수 |

## 1. 서비스 특성과 리스크 관점

- **짧은 시간, 소수 인원, 높은 동시성**: 행사 1회에 참가자 수십 명이 같은 순간(체크인·입장등록·투표 마감)에 접속합니다. 트래픽 총량보다 **같은 데이터를 동시에 건드리는 경합**이 핵심 리스크입니다.
- **상태 기계가 단일 행에 집중**: 행사 상태(`P → S → V → X`)와 현재 턴(`current_round`)이 `event_rounds` 한 행에 있고, 관리자 조작·스케줄러·참가자 요청이 모두 이를 기준으로 판단합니다.
- **현장 운영 서비스**: 사용자는 운영자(수 명)와 참가자이며, 장애 시 **현장에서 사람이 즉시 복구할 수 있는 수단**이 중요합니다. (되돌리기 기능을 일부러 제공)

### 설계 원칙 (회고 시점에서 정리)
1. **서버가 항상 기준**이다. 화면(WebSocket 포함)은 UX이고 정합성은 서버 검증과 DB 제약이 책임진다.
2. **검증 + DB 제약 + 충돌 처리** 3단으로 방어한다. (검증만으로는 동시성에서 뚫린다)
3. **상태를 저장하지 않고 계산**해서 동기화할 상태를 줄인다. (턴별 좌석 미저장)
4. **느린/불안정한 외부 호출은 격리**한다. (Queue Job + 재시도)
5. **막을 수 없는 실수는 되돌릴 수 있게** 한다. (로테이션·매칭·종료 되돌리기)

## 2. 문제 상황별 대비 기록

각 항목은 **상황 → 원인 → 현재 대응 → 남은 위험 → 후속 과제** 순서입니다.

### 2-1. 로테이션 진행 버튼 동시/중복 클릭

- **상황**: 관리자 두 명이 동시에 진행을 누르거나, 한 명이 연타한다.
- **원인**: `current_round` 를 읽고 +1 해서 쓰는 Read-Modify-Write 경합. 순차 중복은 별개 문제(멱등성).
- **현재 대응**
  - `SeatingService::rotateProgress()` 가 트랜잭션 안에서 `EventRound::lockForUpdate()` 로 행사 행에 **비관적 락**을 건 뒤 갱신 → lost update 방지.
  - 락을 잡은 상태에서 `next > maxRound` 이면 거부 → **마지막 턴 초과 방지**.
  - 같은 방식의 락을 `rotateBack`, `setRotationLimit`, `cancelVoting`, `reopenFromClosed` 에 적용.
  - 락 범위가 "행사 1행"이라 **다른 행사끼리는 서로 막지 않음**.
- **남은 위험**: 락은 *경쟁 상태*만 막는다. 연타가 순차로 처리되면 정상적으로 +2 가 된다.
- **임시 안전망**: `rotateBack` (직전 턴 복구).
- **후속 과제**: 요청에 `expected_round` 를 실어 `current_round` 와 일치할 때만 +1 (낙관적 동시성). 불일치 시 "이미 진행되었습니다" 응답.

### 2-2. 체크인 번호표 중복 배정

- **상황**: 현장에서 호스트 여러 명이 동시에 체크인하여 같은 번호가 나간다.
- **원인**: "빈 번호 조회 → 저장" 사이에 다른 요청이 끼어드는 check-then-act.
- **현재 대응**
  - `event_rosters` 에 `UNIQUE(event_id, gender, ticket_no)` → **DB가 최종 방어선**.
  - 자동 배정(`rosterToggleCheckIn`)은 유니크 위반(`UniqueConstraintViolationException`) 시 **다음 빈 번호로 최대 3회 재시도**(`AUTO_RETRY`), 초과하면 "번호표가 겹쳤습니다. 다시 시도해 주세요"로 빠르게 실패.
  - 번호 변경(`rosterSetTicket`)은 트랜잭션 + 명단 행 `lockForUpdate()` 후 중복 확인.
- **선택 이유**: "다음 빈 번호"는 여러 행을 보고 계산하는 값이라 행 락으로 보호하기 어렵고, 유니크 제약이 가장 싸고 확실한 직렬화 지점이다. 락 대비 데드락·경합 위험이 없다.
- **남은 위험**: 없음(명단 기준). 단, 입장등록 쪽 번호표는 2-6 참고.

### 2-3. 매칭 선택(투표) 중복 저장 · 연타

- **상황**: 같은 선택을 여러 번 저장하거나, 저장을 연타한다.
- **현재 대응**
  - `event_votes` 에 `UNIQUE(event_id, voter_id, target_id)` → 같은 상대 중복 지목은 DB가 차단.
  - `saveVotes` 는 전체 삭제 후 재삽입이 아니라 **차집합(diff) 반영**: 빠진 상대만 삭제, 새 상대만 insert, 유지분은 불변. 전체가 `DB::transaction`.
  - 결과적으로 **같은 요청을 몇 번 보내도 결과가 같다(멱등)**. 바꾸지 않은 투표의 `created_at` 도 보존.
  - 대상 검증을 서버에서 재수행: 같은 행사 · 이성 · 본인 제외 · 최대 3명(`max:3`, `distinct`).
  - 라우트 `throttle:20,1` 로 과도한 연타 차단.
- **남은 위험**: 최대 3명 제한은 **요청 단위 검증**이라, 서로 다른 두 요청이 동시에 들어오면 합쳐서 초과할 수 있다. (실제 발생 가능성은 낮음: 한 사람이 한 기기에서 순차 저장 + throttle)
- **후속 과제**: 투표자 단위 락(회원 행 `lockForUpdate`) 후 최종 개수 재확인.

### 2-4. 투표 마감 경계 (마감 직전 저장)

- **상황**: 마감 시각 직전/직후에 요청이 도착한다. 화면은 아직 열려 있다.
- **현재 대응**
  - 저장 시마다 `EventRound::isMatchSelectable()` 로 **서버가 선택 가능 기간을 판정**(와인파티: V 상태 + 자동 마감 시각 이전 / 1:1: S·V 동안).
  - 늦은 요청은 서버에서 거부. 화면은 `EventClosed` 브로드캐스트로 즉시 갱신(UX 용도).
- **결과**: 화면 상태와 무관하게 데이터는 안전.

### 2-5. 수동 마감과 자동 마감(매일 9시)의 겹침

- **상황**: 관리자가 수동 마감하는 순간 스케줄러도 같은 행사를 마감한다.
- **현재 대응**
  - 스케줄러는 `withoutOverlapping()` 으로 **자기 자신끼리의 중복 실행 방지**, 대상은 `status = V` 인 행사만 조회, 조건은 `now() >= 자동 마감 시각`.
  - 조건이 "지난 시각" 기준이라 **배포/재시작으로 한 번 놓쳐도 다음 실행에서 밀린 행사를 일괄 마감**(자기 치유).
  - 마감 후 운영진 텔레그램 리포트는 `SendCloseVotingReportJob`(Queue, `tries=3`, `backoff=10s`)으로 분리 → 외부 API 지연/실패가 **마감 자체를 막지 않음**.
- **남은 위험**: `closeVoting` 에는 락과 "이미 종료면 무시" 가드가 없다. 두 경로가 겹치면 상태는 같지만 **리포트가 두 번 발송**될 수 있다. 이는 `openVoting` 도 동일.
- **후속 과제**: 락 + 이미 목표 상태면 no-op 반환, Job 에 `ShouldBeUnique`(행사 ID 기준).

### 2-6. 입장등록 경합과 반쪽 데이터

- **상황 A — 같은 번호표로 동시에 입장등록**: 검증(`checkRegistrableTicket`)은 둘 다 통과할 수 있다(TOCTOU). 전화번호는 `UNIQUE(event_id, phone)` 로 DB 차단되지만 **회원 테이블에 번호표 유니크가 없다**.
- **상황 B — 가입 중간 실패**: `Member::create` 후 `RotationSeat::create` 가 실패하면 좌석 없는 회원이 남는다. (현재 두 insert 가 한 트랜잭션이 아님)
- **후속 과제**
  - `members` 에 `UNIQUE(event_id, gender, name)` 추가(기존 데이터 중복 점검 선행).
  - 두 insert 를 `DB::transaction` 으로 묶기.

### 2-7. 메시지 전송 횟수(1인 5회) 제한 우회

- **상황**: 전송 버튼 연타/동시 요청.
- **원인**: `count()` 로 확인 후 `create()` 하는 check-then-act.
- **현재 대응**: 상태(S/V) 검증, 수신자 검증(같은 행사 이성), 입력 길이 제한.
- **남은 위험**: 동시 요청 시 5회를 초과할 수 있음.
- **후속 과제**: 발신자 행 락 후 재확인, 또는 카운터 컬럼 + 조건부 UPDATE(`WHERE sent < 5`).

### 2-8. 실시간(WebSocket) 이벤트 유실·순서 문제

- **상황**: 모바일 네트워크 전환/잠금으로 연결이 끊겨 `RotationUpdated`, `EventClosed` 등을 놓친다.
- **현재 대응**
  - 알림은 "변경 신호"일 뿐, 화면은 이벤트 수신 시 서버에서 필요한 prop 을 **다시 조회**(`router.reload({ only: [...] })`)한다. 즉 이벤트에 상태를 실어 보내지 않는다.
  - 게임 탭처럼 상태 의존 UI 는 이벤트 수신 시 노출 조건을 재조회하고, 게임 화면에 있으면 홈으로 이동.
- **남은 위험**: 연결이 끊긴 동안의 이벤트는 재접속 후에도 수신되지 않는다. 페이지 이동/새로고침 전까지 이전 화면이 보일 수 있음.
- **후속 과제**: 재연결(`connected`) 시점과 탭 포커스 복귀 시 전체 재조회, 필요 시 주기적 보정 폴링.

### 2-9. 휘발성 게임 집계(테이블 Yes/No)

- **상황**: 같은 테이블 사람들이 동시에 응답, 늦게 도착한 이전 질문 응답, 데이터 누적.
- **현재 대응**
  - 집계를 DB가 아닌 **Redis Hash** 에 두고 `HINCRBY`(원자 연산)로 증가 → 동시 응답에도 유실 없음.
  - 현재 질문 인덱스(`q`)와 다르면 응답을 **무시**(stale 응답 방어).
  - 키에 TTL(6시간)로 자동 정리. private 채널 인증은 **현재 좌석 기준**.
- **의도된 트레이드오프**: 익명 아이스브레이킹이라 **사용자별 중복 응답 방지는 하지 않음**. (정합성이 중요한 데이터가 아님)
- **참고**: `q` 기록(`HSET`)과 `HINCRBY` 가 분리되어 있어 극히 드물게 첫 응답 경합이 있을 수 있으나 결과에 영향이 미미함.

### 2-10. 외부 서비스(텔레그램) 장애

- **상황**: 외부 API 지연/오류.
- **현재 대응**: 호출을 트랜잭션 밖 + Queue Job 으로 분리, 재시도 3회/10초 간격. 실패해도 마감 등 핵심 흐름은 성공.
- **후속 과제**: 실패 Job(`failed_jobs`) 모니터링 및 알림, 필요 시 재처리 절차를 운영 문서에 명시.

### 2-11. 서버 재시작 · 배포 중 행사 진행

- **상황**: 행사 도중 서버가 재시작된다.
- **현재 대응**: 핵심 상태는 DB(`current_round`, 상태), 좌석은 **계산식**이라 복구해야 할 인메모리 상태가 없다. Redis 게임 집계는 휘발을 허용.
- **후속 과제**: 행사 시간대 배포 금지 규칙, 배포 직후 헬스 체크 항목 정리.

### 2-12. 운영자 실수(되돌리기 수단)

| 실수 | 복구 수단 |
|---|---|
| 로테이션을 한 번 더 진행 | `rotateBack` (직전 턴) |
| 매칭 시작을 잘못 누름 | `cancelVoting` (투표 데이터 유지) |
| 매칭을 잘못 종료 | `reopenFromClosed` (타입별 직전 상태로 복구) |
| 이미 입장등록한 번호의 체크인 취소 | 서버가 거부 + 사전 안내 |

→ "막을 수 없는 실수는 되돌릴 수 있게 한다"는 원칙의 결과물.

## 3. 멱등성 점검 요약

| 영역 | 방식 | 판정 |
|---|---|---|
| 매칭 선택 저장 | 목표 상태 반영(diff) + 유니크 | ✅ 멱등 |
| 입장등록 | `UNIQUE(event_id, phone)` + 검증 | ✅ 중복 불가 |
| 일일 통계 스냅샷 | `updateOrCreate` + `unique(snapshot_date)` | ✅ 재실행해도 1행 |
| 상세페이지·멘트 저장 | `updateOrCreate`, 유형별 `unique` | ✅ |
| 정기 작업 | `withoutOverlapping()` | ✅ 겹침 방지 |
| 체크인 토글 | 상태 기반 분기(참석이면 취소) | ◐ 두 번 = 원복 |
| 매칭 마감 / 시작 | 상태 세팅만, 가드 없음 | ◐ 부수효과(리포트) 중복 가능 |
| 로테이션 진행 | 락 직렬화 + 상한 | ❌ 연타 시 +2 (되돌리기로 보완) |

**교훈**: 멱등하게 만드는 핵심은 요청을 "명령(+1)"이 아니라 **"목표 상태(이 집합으로 맞춰라)"** 로 표현하는 것. 증분 명령(+1)은 구조적으로 멱등하지 않으므로 낙관적 락(`expected_*`)이나 멱등 키가 필요하다.

## 4. 잘한 점 / 아쉬운 점

### 잘한 점
- 동시성 핵심 지점(행사 상태 전이, 번호표)에 **락 또는 DB 제약**을 일관되게 적용했다.
- 상태 저장을 최소화(턴별 좌석을 계산)해 **정합성 문제의 표면적 자체를 줄였다**.
- 느린 외부 연동을 Job 으로 분리해 **핵심 흐름과 장애를 격리**했다.
- 실수 복구 기능을 제공해 **현장 운영 리스크를 낮췄다**.
- 서버 재검증 원칙으로 화면 상태와 무관하게 데이터를 보호했다.

### 아쉬운 점
- 일부 흐름(마감·시작, 횟수 제한, 가입)이 **"확인 후 쓰기"** 에 머물러 있다.
- 동시성·멱등성 **자동 테스트가 거의 없다.** (현재 테스트는 일부 단위/기능 테스트 중심)
- 락·캐시·큐 설정이 환경에 따라 달라질 수 있다. `.env.example` 기본값은 `CACHE_STORE=file`, `QUEUE_CONNECTION=database` 이므로 **다중 인스턴스에서는 캐시 락을 신뢰할 수 없다.** (현재 락은 DB 행 락 중심이라 영향이 작음)
- 비밀번호 4자리 평문 저장은 **요구사항에 따른 의도된 선택**이지만, 확장 시 해시/시도 제한/일회성 링크로 전환이 필요하다.

## 5. 결정 사항 (Decisions)

| # | 결정 | 이유 |
|---|---|---|
| D1 | 상태 전이는 행사 행 비관적 락으로 직렬화 | 락 범위가 작고 단순, 행사 간 독립 |
| D2 | 번호표 충돌은 유니크 제약 + 재시도로 해결 | 다행 계산 값이라 행 락이 부적합 |
| D3 | 매칭 선택은 diff 반영으로 멱등하게 | 연타·재전송 안전, 생성 시각 보존 |
| D4 | 게임 집계는 Redis 휘발 처리 | 영속 불필요, 원자 증가 |
| D5 | 외부 알림은 Queue Job 으로 분리 | 응답 지연·장애 격리 |
| D6 | 실수 복구용 되돌리기 기능 제공 | 현장 운영에서 복구 시간이 곧 비용 |
| D7 | 비밀번호 평문 유지 | 현장 대면 확인 요구사항 (재검토 대상) |
